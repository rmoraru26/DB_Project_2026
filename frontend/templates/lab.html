Step 1 of 9

What a MariaDB audit plugin is

Every connection, every opened table and every finished statement passes through the server's audit API. campus_audit is a shared library (campus_audit.so, C++, MYSQL_AUDIT_PLUGIN) that the server loads with INSTALL SONAME 'campus_audit'. From then on its callback runs inside mariadbd and appends one JSON line per event to a log file.

Application logging sees…

only what one application decides to log, only for that application.

The server plugin sees…

every client of the server (this web app, the mariadb CLI, any script), including failed logins, rejected statements and schema changes, and replaces every value in a statement by ? before it writes.

In this tour you will

  1. ask the server whether the plugin is loaded and how it is configured;
  2. run allow-listed statements against a disposable table of your own;
  3. read the plugin's records and the trigger's row history side by side;
  4. see three places where the plugin's view of the server ends.

How it fits together

campus_audit plugin

Called by the server for the TABLE, GENERAL and CONNECTION event classes. Knows who (database account), which table, which statement (as a digest without values) and whether it worked (error code). Writes a JSON Lines file, because writing tables from inside an audit callback would re-enter the server.

SQL triggers

Run inside the changing statement and store what changed in the row (old and new values as JSON) in audit_events. They never see failed statements, DDL or logins: the audit API is the only place that does.

The two are joined by the connection id: CONNECTION_ID() in a trigger row equals conn in a plugin record.

Check the plugin

The page asks the running server, with the web app's own unprivileged account:

SELECT PLUGIN_STATUS, PLUGIN_TYPE, PLUGIN_LIBRARY, PLUGIN_MATURITY, ...
  FROM information_schema.PLUGINS WHERE PLUGIN_NAME = 'campus_audit';
SHOW GLOBAL STATUS    LIKE 'campus\_audit\_%';
SHOW GLOBAL VARIABLES LIKE 'campus\_audit\_%';

Your lab rows

The plugin's records

These records were written by campus_audit inside the server while your statement ran, then imported with CALL campus_audit.import_current_log() and read back from campus_audit.plugin_events, filtered by your request's connection id. Open a record to see what each field means and the raw JSON line.

Row history from the triggers

A different mechanism: the AFTER triggers in database/triggers.sql wrote these rows into audit_events in the same statement. They hold the row's values, which the plugin never sees, and the application user id (@app_user_id) that the web app asserts on every connection.

Where the plugin's view ends

Each limit below is something you can reproduce in step 4, or that the test suite checks.

“Opened for write” is not “changed”

TABLE events fire when the server opens and locks a table, before the statement runs. Insert an invalid row still produces a table_write record; only the statement record after it carries error_code 4025, and no trigger row exists.

Statements, not commits

After Update, then ROLLBACK the plugin reports status: ok, because the statement did succeed. The trigger row was rolled back with the transaction. No audit event announces COMMIT or ROLLBACK of the rows.

Refused before any table is opened

The privilege check runs before the server opens a table, so a forbidden statement raises no TABLE event at all. Version 1.0 of the plugin therefore left no trace of it; version 1.1 records it from the GENERAL STATUS event when the session's default schema is watched (access_denied: true). A refused statement that names another schema explicitly is still invisible.

Values never reach the plugin

No audit event carries row values. Your label appears in the trigger's new_values, but in the plugin's sql_digest it is ?: the plugin removes every literal on purpose.

Database account, not person

Every web request uses the shared account campus_app; the plugin cannot know which student acted. Only the trigger row has application_user_id, and that is an assertion of the client (SET @app_user_id), not something the server verified.

Observe, never block

The audit callback returns void: a plugin can watch but cannot veto. When the log cannot be written, statements still succeed, the state becomes DEGRADED and an audit_gap record later states how many records were lost (tested with /dev/full and a locked file).

CHANGE_USER names the old account

A COM_CHANGE_USER event describes the session before the switch, even when the switch fails. A failed switch therefore names the current account, not the one somebody tried to become (measured with mysql_change_user() in the end-to-end tests).
